# AI技术问答生成

根据候选人简历生成偏技术深挖的面试问答题目，保存到 `面试官/面试问答/` 目录。

> 本命令是原 `/问答生成` 的无歧义版本，适用于 AI 应用开发、算法工程化、AI Infra、后端/平台工程、技术型 AI 产品等需要深挖技术方案的面试。若候选人为 AI 产品经理，且本轮重点是产品判断、STAR/BEI 行为验证、业务场景和 0-1 落地，请使用 `/AI产品问答生成`。

---

## 参数解析

从用户调用命令时附带的自然语言中解析候选人姓名、简历文件名和可选关注方向。若用户使用 `@` 引用具体简历或目录，以引用内容为准。

文件名日期使用当前日期，格式为 `{YYYY-M-D}`。如上下文中没有可靠日期，使用 `Shell` 执行 `date +%Y-%-m-%-d` 获取。

## 操作步骤

1. 使用 `Glob` 在 `面试官/候选人简历/` 下定位简历文件：`面试官/候选人简历/*{姓名}*.md`。
2. 使用 `ReadFile` 读取候选人简历，以及下方“参考资料”列表中的文件。
3. 对简历中的技术点、项目方案、缩写、版本敏感信息和可疑 OCR 文本执行下文「联网校验规则」。
4. 对照 `面试官/招聘配置/岗位人才画像.md` 判断候选人匹配度、必备项缺口、加分项、强风险和本轮必须验证的能力项。
5. 结合 `面试官/招聘配置/面试官信息.md`、岗位方向和候选人简历执行「考察维度选择规则」。
6. 按下方输出模板生成问答，并使用文件编辑工具创建 `面试官/面试问答/{YYYY-M-D}-{姓名}-AI技术面试问答.md`。

## 文件命名

`{YYYY-M-D}-{姓名}-AI技术面试问答.md`，日期为当前日期。

## 联网校验规则（清单式判断，必须执行）

**不要凭“我知道”直接写期望答案。** 在生成问答文档之前，按以下步骤完成校验。

### 第 1 步：枚举待核查项

在思考过程中列出简历中出现的所有：

- 框架、库、SDK、平台（含版本号）
- 候选人声称的“自研 / 优化 / 重构 / 性能提升 X%”项
- 架构方案、工程实践（RAG / Agent / AI Coding / 推理优化 / 评估方案等）
- 缩写、内部平台名、非主流工具

### 第 2 步：逐项对照触发条件

每一项都要明确判断以下 4 个问题，任一项为“是”即触发搜索：

- **版本敏感**：它是否在最近 12 个月有重大版本更新或能力变化？
- **声称强能力**：候选人是否声称使用了“新特性 / 自研优化 / 显著性能提升”？
- **非通用**：它是否是缩写、内部平台、非主流方案、或社区资料稀少的工具？
- **下钻细节**：准备写入“期望答案”的内容是否包含具体 API、参数、行为边界、版本特性？

### 第 3 步：触发即调用联网工具

- 触发的项必须调用 `WebSearch` 后再写期望答案；需要看官方原文细节时配合 `WebFetch` 抓取页面。
- 查不到公开资料的内部平台或非公开方案，在追问设计中标注“需面试官现场澄清”，不要臆造期望答案。
- 不设调用次数上限或下限，按清单驱动。

### 第 4 步：输出前复盘

在生成文档前，在思考过程中明确：

- 共识别多少个待核查项。
- 哪些项触发搜索，触发原因是什么。
- 已对触发项调用 `WebSearch` / `WebFetch`，或说明未触发的理由。
- 未触发的项默认采用本地知识库和通用工程常识，但避免写成未经验证的强事实判断。

### 第 5 步：期望答案中的事实陈述必须可溯源

在**期望答案、追问设计、面试官提示**中出现的任何强事实主张，包括但不限于：

- “业内主流方案是 X” / “新一代模型都用 Y” / “公认做法是 Z”
- “X 厂商 / X 团队使用 Y 技术” / “X 项目方法是 Y”
- “某论文 / 某框架支持 Z 能力” / “X 方法是 Y 年由 Z 提出”
- “某模型在某 benchmark 的指标是 X”
- “X 是 Y 时代的标准做法 / 已经过时”

必须满足以下之一：

1. 已通过 `WebSearch` / `WebFetch` 在本次执行中校验，并在思考过程中保留校验结论。
2. 在该句子末尾标注 `[需面试官现场校验]`，提醒面试官不要把它当既定事实。

禁止基于模型印象写入“业内 / 大家 / 主流 / 公认 / 据传”等强事实措辞；禁止凭印象引用具体年份、作者、benchmark 数字或论文名。

### 第 6 步：警惕简历 OCR 错误

`面试官/候选人简历/` 下的 Markdown 简历可能来自 `面试官/候选人简历/image/` 图片 OCR，可能存在识别错误。直接把 Markdown 当事实信任会把错误传导到面试问答里。

满足任一条件即视为可疑，必须校验：

- 出现非工业界标准术语。
- 出现字面通顺但语义奇怪的搭配。
- 出现生僻字、形近字、大小写异常或字符混淆。
- 简历某段表述明显不连贯或语法不通顺。

校验方法必须执行其一：

1. 使用 `WebSearch` 搜索该术语，看是否为标准说法。
2. 使用 `Glob` 找到 `面试官/候选人简历/image/` 下对应原图，并用 `ReadFile` 回读图片确认。
3. 在追问设计中加 `[需面试官现场与候选人核对原文]` 警示标签。

## 考察策略

本命令以技术深度为核心，但必须服从公司面试规范：

- 生成任何问题前，必须先读取 `面试官/招聘配置/岗位人才画像.md`，并明确本轮技术面要验证的画像能力项。
- 专业能力评估应聚焦 2-4 个核心能力项，不要无限发散。
- 技术追问必须锚定简历中的具体项目、技术栈、工具、架构和指标。
- 通过 STAR（情境-任务-行动-结果）追问验证候选人是否真做过。
- 通过 BEI（行为事件访谈）嵌入观察协作、学习、抗压和问题解决能力。
- 对每道题标注“本题考察 / 本题不考察”，避免跑偏。
- 对面试官本人不负责的最终录用、薪资、终审文化价值观，不做越权判断。

## 内容规则

1. **技术核心，深度优先**：技术深挖是本命令主要目标，但素质能力在技术追问中自然观察。
2. **紧扣简历细节**：专业题必须锚定简历中的具体项目、技术栈和工具。
3. **梯度递进**：每道题设计为“基础问题 + 2-3 个递进追问”。
4. **业内实践对标**：对核心技术方案可联网检索公开实践，作为面试官背景知识。
5. **技术边界清楚**：如果面试官背景不适合深挖某类算法或底层实现，应明确留给下一轮专业面试官。
6. **时间把控**：问题数量符合 55 分钟面试规划，优先深度而非广度。
7. **专业名词标注**：对专业名词进行中文标注，格式为 `英文术语（中文释义）`。
