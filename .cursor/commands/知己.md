# 知己

输入：$ARGUMENTS

今天日期：!`date +%Y-%-m-%-d`

## 操作步骤

1. 从 $ARGUMENTS 中解析：第一个文件路径是 `JD人才画像.md`，后续 `@` 引用的文件是候选人的个人材料。
2. 使用 `Read` 读取 `JD人才画像.md` 和所有个人材料文件。
3. 使用 `Glob` 在候选人目录下查找已有的对标表、简历、STAR库、行为画像等（避免遗漏已有产出）。
4. 读取下列共享知识：
   - `共享知识/面试方法/01 面试官手册.md`
   - `共享知识/面试方法/02 人才选拔与面试技巧.md`
   - `面试官/招聘配置/面试评价标准.md`

## 产出物

本命令生成三个文件，均存放到 `{JD人才画像所在目录}/`：

| 文件 | 用途 | 消费者 |
|------|------|--------|
| `对标表.md` | JD-我逐条对照（7列） | `/简历定制`、`/面试准备` |
| `STAR库.md` | 可复用的 STAR 故事骨架 | `/面试准备`（匹配而非推导） |
| `行为画像.md` | 候选人的行为特质画像 | `/面试准备`（个性化素质题预测） |

## 第一阶段：生成对标表

### 整体阅读

- 阅读所有个人材料
- 为每项 JD 能力从材料中提取已有的事实、数字、经历
- 预填"我的证据"草稿
- 对每条证据标注来源文件和置信度：
  - **✅ 已确认**：材料中明确记载 + 候选人确认
  - **🔍 AI提取**：从材料中提取，待候选人确认
  - **⚠️ 需补充**：材料中无直接证据，标记缺口

### 多源交叉验证

如果候选人提供了多份材料（如旧简历 + 周报 + 绩效总结），进行交叉核对：

- 同一段经历在不同材料中的日期是否一致？
- 同一角色在不同材料中的职责描述是否有出入？
- 同一个数字在不同材料中的口径是否相同？

发现冲突时列出，让候选人裁决：
```
## 材料交叉核对发现的不一致

1. **角色名称 - [公司名]：**
   旧简历中写："高级产品经理"
   绩效总结中写："AI产品经理"
   → 以哪个为准？

2. **时间范围 - [项目名]：**
   旧简历：2023.06 - 2025.11
   项目复盘：2023.09 - 2025.06
   → 以哪个为准？
```

### 逐条确认

- 逐条展示预填的"我的证据"和"缺口"
- 让候选人确认、修正、补充
- 对不清晰的地方追问具体细节（"这段经历中你个人贡献的比例是多少？""这个决策当时有谁反对？"）
- 将候选人确认过的证据从 🔍 更新为 ✅

### 缺口处理

- 对完全无证据的能力项，标记"本轮无直接证据"
- 和候选人讨论：这条是真的没做过，还是材料没覆盖？
- 真的没做过 → 如实标记缺口，讨论怎么弥补
- 材料没覆盖 → 你口头补充证据

### 对标表结构

| JD 能力项 | 面试官验证点 | 强信号 | 红旗信号 | 我的证据 | 缺口 | 弥补/回应策略 |
|-----------|------------|--------|---------|---------|------|--------------|
| AI 预填 → | AI 预填 → | AI 预填 → | AI 预填 → | ← 你填 | ← 你填 | ← 你填 |

前 4 列从 `JD人才画像.md` 导出，不需要候选人填写。

### 保存

逐条确认后，保存完整对标表到 `{JD人才画像所在目录}/对标表.md`。

## 第二阶段：生成 STAR 故事库

对标表确认完毕后，从"我的证据"列中提取候选人最核心的经历，转为可复用的 STAR 骨架。

### 选取原则

- 选择对标表中"证据最强"的经历（有具体数字、有角色边界、有决策过程）
- 优先选择能覆盖多条 JD 能力项的经历（一条经历 → 多个 STAR 角度）
- 选取 4-6 条核心经历

### STAR库.md 结构

```markdown
# STAR 故事库

> 由 /知己 生成（{日期}）。
> 每次 /面试准备 从此库匹配最相关的故事做 JD 化微调，而非从零推导。
> 当有新的关键经历时，重新运行 /知己 更新此库。

## 使用说明

- 每个故事标注了 **Use for** 标签，表示可以回答哪类面试问题
- `/面试准备` 根据 JD 自动匹配，只需微调细节，不需重新组织 STAR
- 候选人在面试前需亲自过一遍每个故事的数字和细节

---

## 故事1: [描述性标题，如"AI游戏引擎0-1产品化"]

- **来源**：[公司/项目，时间段]
- **覆盖的JD能力项**：[对标表中的能力项编号]
- **Use for**：
  - "[可以回答的问题类型1]"
  - "[可以回答的问题类型2]"
  - "[可以回答的问题类型3]"
- **S** (Situation)：[背景、参与方、当时面临的挑战]
- **T** (Task)：[你的职责、目标、成功标准]
- **A** (Action)：[你的具体动作——区别于团队做了什么]
- **R** (Result)：[量化结果、影响范围]
- **数字准备**：[这个故事里每个数字的来源、口径、上下文——确保面试被追问时答得上来]
- **角色边界**：[本人贡献 vs 团队/同事贡献的清晰分界——面试官大概率会追问"这是你做的还是团队做的"]
- **追问题预演**：[面试官最可能追问哪个细节、为什么、怎么回答]
```

### 约束

- 只从对标表"我的证据"列中已确认（✅）的经历提取
- 每条 STAR 的数字准备必须包含数字的来源和计算口径
- 角色边界必须诚实：如果某个成果是团队努力，"你的贡献占比"必须明确
- Use for 标签覆盖不同类型的面试问题（项目推动类/决策类/协作类/失败复盘类）
- 保存到 `{JD人才画像所在目录}/STAR库.md`

## 第三阶段：生成行为画像

基于对标表"我的证据"列中的经历，结合 JD人才画像 的"强信号/红旗信号"，生成候选人的行为特质画像。

### 提取规则

从经历中归纳，不凭空推断：

| 从经历中提取 | 行为信号 |
|-------------|---------|
| 多次出现"0到1"经历 | 探索型——在不确定环境中找到方向 |
| 多次提及"推动跨团队/跨角色协作" | 枢纽型——连接不同角色推动结果 |
| 经历中有明显的"数据驱动决策" | 证据型——靠数据而非直觉判断 |
| 经历中有"独立Owner某方向" | 自主型——能独立负责、主动推进 |
| 经历中有"从失败中调整方向" | 韧性型——能接受失败并调整 |

### 行为画像结构

```markdown
# 行为画像

> 由 /知己 生成（{日期}）。基于候选人的经历，结合 JD 的强信号/红旗信号。
> 被 /面试准备 读取，用于生成个性化的素质能力题预测和模拟面试反馈。

## 核心行为特征

[从经历中归纳的 3-5 个行为模式，每个附带一段经历作为证据]

- **探索型**：在多个项目中展现了从 0 到 1 的能力。证据：XX 项目和 YY 项目均为从零搭建。
- **枢纽型**：...
- ...

## 与目标岗位的行为匹配

基于 JD人才画像 的"强信号/红旗信号"，评估行为风格的匹配度：

| 行为特质 | 岗位期望 | 匹配度 | 说明 |
|---------|---------|--------|------|
| [特质1] | [JD中的对应期望] | ✅ 强匹配 / ⚡ 可匹配 / ⚠️ 需注意 | [一句话] |
| ... | ... | ... | ... |

## 可能触发面试官追问的行为信号

- [哪些行为特质可能被面试官视为红旗，建议准备回应]
- [哪些行为特质是加分项，面试中应主动展示]

## 工作风格偏好

- **决策方式**：[从经历中推断：数据驱动 / 直觉驱动 / 共识驱动]
- **协作风格**：[从经历中推断：独立Owner / 紧密协作 / 灵活切换]
- **最适合的环境**：[从经历中推断：创业型/成熟型/转型期/从0到1]
- **需要警惕的环境**：[与行为特质可能冲突的环境]
```

### 约束

- 每一项结论必须附带至少一段经历作为证据（"因为XX经历中的YY表现"）
- 不做心理学评估（不做 DISC/MBTI 等测试推断），只做行为模式归纳
- 不确定性高的推断标注为"初步推断，建议你确认"
- 保存到 `{JD人才画像所在目录}/行为画像.md`

---

## 全局约束

- 绝不编造证据。材料里没有的，标记"需要你补充"而不是 AI 代写。
- 不替候选人判断"这个证据够不够强"——只标注"此证据可直接映射到JD能力项"或"需进一步补充细节"。
- 追问不委婉——如果一段经历没有具体数字、没有角色边界、没有决策过程，直接指出。
- STAR 库和行为画像的每一项结论必须可追溯到对标表中的具体证据。
- 三个产出物完成后，提醒候选人：可继续运行 `/简历定制` 和 `/面试准备`。
