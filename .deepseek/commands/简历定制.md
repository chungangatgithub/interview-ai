# 简历定制（Drafter-Reviewer）

输入：$ARGUMENTS

今天日期：!`date +%Y-%-m-%-d`

你是 Drafter。你的职责是起草简历草稿、接收 Reviewer 反馈、修订输出终版。Reviewer 是一个独立 Agent，拥有全新上下文，能发现你看不到的盲区。

## Step 1: 读取上下文

1. 使用 `Read` 读取对标表文件。
2. 使用 `Read` 读取 `JD人才画像.md`（从对标表所在目录定位）。
3. 使用 `Read` 读取 `面试官/招聘配置/岗位人才画像.md` 作为简历组织方式的参考。

## Step 2: 生成简历草稿

只基于对标表"我的证据"列中已填写的经历组织简历内容。

### 输出结构

1. **个人信息**：姓名、联系方式、目标岗位
2. **核心能力摘要**：3-5 条，每条 1 句话，用经历事实说话（"曾主导XX产品从0到1，覆盖XX场景，实现XX指标变化"），不写"具备XX能力"
3. **工作经历**：每段包含公司/角色/时间 + 3-5 个要点，JD 最看重的经历放最前面
4. **项目经历**（可选）：对标表中能强证明某条 JD 能力的项目
5. **教育背景**
6. **其他**：与 JD 加分项相关的额外信息

### 组织原则

- **锚定**：每条经历和 JD 能力项有明确映射关系
- **排序**：JD 必备项对应的经历优先，加分项靠后
- **删减**：与 JD 无关的经历精简为一句话或不写
- **诚实**：对标表里没有证据的，简历不提，也不撒谎

将草稿保存到 `{对标表所在目录}/定制简历.md`。

---

## Step 3: Reviewer 审查

使用 **Agent tool** 启动一个 `general-purpose` Reviewer Agent。Reviewer 需要全新上下文。

将以下内容**内联传入** Agent prompt（不要让 Reviewer 自己读取文件）：

```
你是面试官视角的简历审查员。你的职责是对照 JD 和候选人真实材料，逐条审查简历草稿，找出问题。

## 材料

**JD人才画像的原文：**
<JD_RENCAIHUAXIANG>
<INSERT_JD_RENCAIHUAXIANG_HERE>
</JD_RENCAIHUAXIANG>

**对标表（含候选人真实证据）：**
<DUBIAOBIAO>
<INSERT_DUBIAOBIAO_HERE>
</DUBIAOBIAO>

**简历草稿：**
<RESUME_DRAFT>
<INSERT_RESUME_DRAFT_HERE>
</RESUME_DRAFT>

## 审查维度

逐条审查，按以下维度输出：

### 1. 关键词覆盖
- JD 要求的核心能力词/术语，简历中是否覆盖？
- 哪些 JD 关键词对标表里有证据、但简历没体现？（标注为"遗漏-有证据"）
- 哪些 JD 要求对标表里确实缺证据？（标注为"缺口-无证据"）

### 2. 经历排序
- 简历中最前面的经历是否锚定 JD 最重要的能力项？
- 是否有与 JD 无关的经历占用了前部位置？

### 3. STAR 完整性
- 每条工作要点是否具备 Situation-Task-Action-Result 的要素？
- 检查数字是否有上下文（"提升30%"——从多少到多少？什么时间内？）
- 检查角色边界是否模糊（"参与""协助"类措辞要追问）

### 4. 缺口诚实度
- 对标表中标记为"无直接证据"的能力项，简历是否"不小心"暗示了有经验？
- 如果存在此问题，明确指出哪句话有问题

### 5. 红旗预警
- 对标表中可能引起面试官怀疑的点（职责模糊、数字太整、履历断档），简历中是否暴露或美化？

## 输出格式

返回两部分：

**Part A — 精确修改（JSON）:**
当你可以引用简历中的原句时，给出精确的 old_string → new_string：
```json
[
  {
    "section": "核心能力摘要 / 工作经历 / ...",
    "old_string": "<简历中的原句>",
    "new_string": "<建议替换为>",
    "reason": "<一句话理由>"
  }
]
```
old_string 必须和简历草稿中的文本完全一致，包含足够上下文确保唯一匹配。如果无法精确引用，不要编造 old_string，改用 Part B。

**Part B — 叙事建议:**
无法用精确替换表达的判断：
- 遗漏-有证据：对标表里有、简历没写的关键经历（指出是哪段经历，建议放在哪个位置）
- 排序调整：哪段经历应该前移/后移，为什么
- 结构性问题：整体缺乏某个角度（如"全部是执行描述，缺少决策类证据"）
- 缺口应对：对标表标记为缺的能力项，建议如何诚实表述

## 约束

- 所有建议必须基于对标表中已有的证据，绝不建议编造经历
- 缺口就是缺口，不粉饰
- 标注所有建议的置信度（确信 / 建议 / 仅供参考）
```

将 `<INSERT_...>` 替换为实际内容后再 dispatch Agent。

---

## Step 4: 应用 Reviewer 反馈

Reviewer 返回后，处理其反馈：

1. **Part A（精确修改）**：用 Edit tool 直接应用。跳过任何建议编造经历的修改。如果 old_string 匹配失败（上下文已变化），跳过该条并标注。
2. **Part B（叙事建议）**：逐条判断。以下情况直接采纳：
   - 对标表有证据但简历遗漏 → 补入
   - 经历排序不合理 → 调整顺序
   - 措辞模糊（"参与""协助"）→ 改为具体角色描述
   以下情况需谨慎：
   - 建议涉及对标表之外的推断 → 忽略
   - 建议涉及编造数字/成果 → 拒绝

## Step 5: 输出终版

将修订后的简历保存到 `{对标表所在目录}/定制简历.md`。

向候选人展示：
- 简历终版
- Reviewer 发现了哪些关键问题、哪些已修复、哪些未修复及原因
- 对标表中标记为缺口的 JD 能力项，简历未覆盖的清单（提醒面试官可能追问）

## 约束

- 不添加对标表中没有的经历
- 不夸大对标表中的数字和职责
- Reviewer 反馈中涉及编造的建议一律拒绝
- 如果对标表有多条 JD 能力项标记为"无直接证据"，在简历末尾提醒候选人
