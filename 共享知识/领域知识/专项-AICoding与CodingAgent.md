## 一、行业演进与产品脉络

### Q1.1 AI Coding 产品是如何演进到 Coding Agent 的？ ⭐⭐

**问题**：
> 近几年 AI Coding 产品是如何从“代码补全工具”演进到“Coding Agent”的？请结合 GitHub Copilot、Cursor、Claude Code 等产品，概括它们代表的阶段变化。

**期望答案**：

**整体演进可以概括为 5 个阶段**：

| 阶段 | 核心形态 | 代表能力 | 产品例子 |
|------|----------|----------|----------|
| **阶段 1：补全助手** | 单行 / 多行补全 | 根据光标附近上下文预测下一段代码 | GitHub Copilot 早期形态 |
| **阶段 2：对话式编程** | Chat in IDE | 解释代码、生成函数、回答报错原因 | Copilot Chat、Cursor Chat |
| **阶段 3：多文件编辑** | Composer / Inline Edit | 根据自然语言修改多个文件、生成 Diff | Cursor Composer 一类能力 |
| **阶段 4：Agent 化执行** | Tool-using Agent | 搜索代码库、读写文件、跑命令、修测试、循环迭代 | Cursor Agent、Claude Code |
| **阶段 5：自治与后台执行** | Background / Subagent / CI Agent | 长任务、并行子任务、检查点、规则、审计 | 新一代 IDE Agent / 云端 Agent |

**关键变化不只是模型更强，而是系统能力增强**：
1. 从“只会生成代码”变成“能理解仓库、调用工具、验证结果”
2. 从“单轮回答”变成“多步闭环：计划 -> 执行 -> 观察 -> 修正”
3. 从“只改当前文件”变成“跨文件、跨目录、跨工具链协同”
4. 从“聊天助手”变成“可受控的执行系统”

**以 Cursor 和 Claude Code 为例的演进特征**：
- **Cursor**：更偏 **IDE 原生**，强调代码库索引、文件级上下文、Diff 可视化、规则（Rules）、记忆（Memories）、MCP 集成，以及从 Chat / Composer 逐步收敛到 Agent 模式
- **Claude Code**：更偏 **终端优先**，强调在真实仓库中执行命令、迭代修改、运行测试、长任务自治、检查点（Checkpoint）、子代理（Subagent）、Hook 和后台任务

**为什么 Coding 会最先 Agent 化**：
1. **反馈可验证**：能用编译、Lint、测试、运行结果验证对错
2. **目标可分解**：需求可以拆成搜索、修改、运行、修复等子任务
3. **环境结构化**：代码库、文件树、依赖关系、Git 历史天然可被工具读取
4. **价值闭环清晰**：能直接衡量完成率、测试通过率、时间节省

**评分要点**：
- 3 分：知道 AI Coding 经历了“补全 -> 对话 -> Agent”的演进
- 4 分：能结合 Cursor、Claude Code 说明产品形态差异
- 5 分：能指出演进本质是“模型 + 工具 + 验证 + 工作流”的系统升级

### Q1.2 Claude Code 和 Cursor 的设计思路有什么差异？ ⭐⭐⭐

**问题**：
> Claude Code 和 Cursor 都在做 AI Coding / Coding Agent，但它们的设计侧重点并不一样。你会如何对比两者的产品形态和系统设计思路？

**期望答案**：

**核心差异可以概括为“终端优先” vs “IDE 原生”**：

| 维度 | Claude Code | Cursor |
|------|-------------|--------|
| **主要交互入口** | 终端优先，后续扩展 IDE | IDE 原生 |
| **核心体验** | 像一个会写代码、跑命令、修问题的工程搭子 | 像一个深度嵌入编辑器的智能开发环境 |
| **上下文获取** | 仓库文件 + Shell + Git + 运行结果 | 编辑器上下文 + 代码库索引 + 文件/符号检索 |
| **任务形态** | 长任务、自治执行、命令驱动更强 | 交互式编辑、多文件改动、可视化反馈更强 |
| **控制方式** | 更强调权限、检查点、回退、Hook | 更强调 Diff、Rules、Memories、MCP、上下文选择 |

**两者共同点**：
1. 都不是单纯“聊天机器人”，而是带工具调用的 Coding Agent
2. 都依赖代码库理解、上下文裁剪、Diff 编辑、测试反馈闭环
3. 都在向更长任务、更强自治、更强工具生态演进

**设计取舍**：
- **终端优先** 的优势：
  - 更贴近真实工程环境
  - 命令、脚本、测试、Git 工作流天然可接入
  - 对后端、基础设施、多仓库开发场景更友好
- **IDE 原生** 的优势：
  - 可视化反馈更强，用户更容易审阅变更
  - 文件上下文、符号跳转、局部编辑体验更自然
  - 更适合日常编码和人机协作式修订

**更本质的差异不是 UI，而是工作流**：
- Claude Code 风格更接近“在真实开发环境里委托一个代理完成任务”
- Cursor 风格更接近“把 Agent 能力嵌到编辑器主工作流里”

**选型建议**：
1. 如果目标是 **本地仓库操作 + 命令执行 + 长任务自治**，终端优先方案更自然
2. 如果目标是 **日常开发提效 + 多文件编辑 + 即时审阅**，IDE 原生方案更有优势
3. 企业产品通常会做 **混合架构**：IDE 负责交互和审阅，执行层走受控沙箱 / 后台 Runner

**评分要点**：
- 3 分：知道两者一个偏终端、一个偏 IDE
- 4 分：能从上下文、任务形态、控制方式上系统对比
- 5 分：能上升到“交互层 vs 执行层 vs 工作流设计”的架构差异

## 二、Coding Agent 核心架构

### Q2.1 一个生产级 Coding Agent 的核心架构应该怎么设计？ ⭐⭐⭐

**问题**：
> 如果让你设计一个生产级的 Coding Agent，支持理解代码库、改代码、运行测试、循环修复，你会如何拆分它的核心模块？

**期望答案**：

**典型架构**：

```
用户请求
   ↓
任务规划器（Planner / Task Manager）
   ↓
上下文引擎（Context Engine）
   ↓
工具路由层（Tool Router）
   ↓
执行层（Read / Search / Edit / Shell / Git / Test / MCP）
   ↓
验证层（Lint / Build / Unit Test / E2E）
   ↓
结果汇总 / Diff 展示 / 用户确认

横向能力：
- 权限与安全策略
- 记忆 / 规则 / 项目约束
- 日志、审计、评估
```

**核心模块拆分**：

| 模块 | 作用 | 关键点 |
|------|------|--------|
| **Planner** | 任务拆解、步骤排序、决定何时调用工具 | 避免一上来就盲改代码 |
| **Context Engine** | 检索相关文件、符号、历史信息 | 决定 Agent 是否“看对代码” |
| **Tool Router** | 选择读文件、搜索、编辑、跑命令等工具 | 不同任务调用不同工具 |
| **Editor** | 生成最小必要修改 | 优先 Diff / Patch，而不是整文件重写 |
| **Verifier** | 运行测试、Lint、构建校验 | 用确定性反馈纠正模型错误 |
| **Policy Layer** | 控制危险操作和权限升级 | 禁止高风险命令直接执行 |
| **Memory / Rules** | 保存项目偏好、编码规范、历史事实 | 减少重复提示，提高稳定性 |

**为什么 Coding Agent 不是“Prompt + LLM”这么简单**：
1. 代码任务不是一次性生成，而是多轮试错
2. 真正难点在于 **上下文选择、工具调度、反馈闭环**
3. 好的 Agent 需要知道什么时候读文件、什么时候跑测试、什么时候停止

**核心闭环**：
1. **Plan**：理解任务并拆解
2. **Act**：读取上下文、修改代码、执行命令
3. **Observe**：观察报错、测试结果、Diff
4. **Verify**：确认是否满足任务目标
5. **Reflect**：若失败则调整策略继续迭代

**评分要点**：
- 3 分：能列出读代码、改代码、跑测试等基本模块
- 4 分：能讲清 Planner、Context、Verifier、Policy 的分工
- 5 分：能说明 Coding Agent 的核心是“工具化闭环系统”而非单次生成

### Q2.2 如何设计支持长任务的自治执行机制？ ⭐⭐⭐⭐

**问题**：
> Coding Agent 在真实项目里经常面对长任务，比如跨模块重构、修复一串失败测试、升级依赖。你会如何设计它的自治执行机制，避免它失控或中途迷失？

**期望答案**：

**长任务的本质问题**：
1. 步骤多，容易偏航
2. 上下文会不断变化
3. 一个动作失败后，需要基于新反馈继续迭代
4. 用户必须保有随时中断、回滚、接管的能力

**推荐机制**：

| 能力 | 设计方式 | 目的 |
|------|----------|------|
| **任务拆解** | 先产出子任务列表和执行计划 | 降低长任务不确定性 |
| **阶段性检查点** | 每轮关键修改前保存状态 | 支持回滚和对比 |
| **工具观察循环** | 每次执行后读取真实输出 | 避免基于臆测继续推理 |
| **停止条件** | 测试通过、目标完成、风险过高时停止 | 防止无限循环 |
| **人工介入点** | 涉及危险命令、批量改动、提交前要求确认 | 保持可控 |
| **并行子任务** | 可将独立任务分派给子代理 | 提升复杂任务吞吐 |

**一个常见的状态机**：

```
待规划
  ↓
执行中
  ↓
观测结果
  ├── 成功 -> 进入下一步 / 完成
  ├── 可恢复失败 -> 调整策略重试
  ├── 高风险操作 -> 等待用户确认
  └── 不可恢复失败 -> 回滚 / 结束
```

**关键设计原则**：
1. **每一步都基于外部观测结果推进**，不要只靠模型“脑补”
2. **尽量缩小单次变更粒度**，每次改一小步更容易验证
3. **把长任务拆成多个可验收节点**，比如“先让编译通过，再修单测，再修 E2E”
4. **允许后台任务和前台任务分离**，例如 dev server 挂后台，主流程继续做代码修改

**与行业产品演进的对应关系**：
- Cursor 一类产品强调 **Agent 模式、后台执行、规则、上下文控制**
- Claude Code 一类产品强调 **检查点、Hook、Subagent、后台任务**
- 这些能力的共同目标都是：让 Agent 能处理更长、更复杂的真实软件工程任务

**评分要点**：
- 3 分：知道长任务需要拆解和循环验证
- 4 分：能设计检查点、停止条件、人工介入点
- 5 分：能上升到状态机、并行子任务、后台任务等自治执行机制

### Q2.3 强编排流程 vs Agent 自主编排，该如何取舍？ ⭐⭐⭐⭐⭐

**问题**：
> 在自建 Coding Agent 系统时，一种思路是做“强编排流程”，把步骤、状态机、检查点、验证规则都明确固化；另一种思路是让 Agent 自主决定搜索、改代码、跑测试、修复的顺序，偏向自主编排。类似 OpenAI 提到的 Harness Engineering，更强调为 Agent 设计环境和反馈回路。你如何比较这两种方案？Claude Code 和 Cursor 更接近哪种？如果自己落地 Coding Agent，不同方案各有哪些优缺点？

**期望答案**：

**先下结论**：
> 这两种并不是非黑即白。生产级 Coding Agent 最佳实践通常是 **“外层强编排 / 强约束，内层 Agent 自主编排”** 的混合模式。

**两种模式的定义**：

| 模式 | 核心思想 | 典型形态 |
|------|----------|----------|
| **强编排流程（Workflow-first）** | 人类或系统预先定义明确步骤、状态流转、验证门槛 | 状态机、DAG、固定节点、强审批流 |
| **Agent 自主编排（Agent-first）** | 给定目标后，由 Agent 自主决定检索、编辑、执行、修复顺序 | ReAct / Tool Loop / Planning Loop / Self-healing Loop |
| **Harness Engineering（约束式自治）** | 不是手工规定每一步，而是构建清晰环境、文档、工具、边界和反馈回路，让 Agent 在其中高效工作 | AGENTS/RULES、可执行计划、Lint、测试、沙箱、检查点、审计 |

**强编排流程的优点**：
1. **可控性强**：适合审批严格、风险敏感的企业场景
2. **结果更稳定**：流程固定，输出更容易预期
3. **易于审计和合规**：每一步都有结构化记录
4. **便于评估和调试**：哪个节点出问题更容易定位

**强编排流程的缺点**：
1. **灵活性差**：遇到未知代码结构或异常路径时容易卡死
2. **维护成本高**：流程越复杂，状态机越难维护
3. **扩展性有限**：新增工具、新语言、新仓库结构时可能要重写流程
4. **容易“过度流程化”**：Agent 像在填表，而不是真正解决问题

**Agent 自主编排的优点**：
1. **泛化能力强**：面对不同仓库和任务时更灵活
2. **对开放任务更有效**：如重构、理解陌生代码、修复复杂测试链路
3. **更接近真实工程问题解决方式**：搜索、试错、修正、再验证
4. **系统升级弹性更大**：模型能力提升后，收益更明显

**Agent 自主编排的缺点**：
1. **不可预测性更高**：可能走弯路、重复操作、上下文漂移
2. **安全风险更高**：若边界不清，容易触发高风险工具调用
3. **调试更难**：失败原因可能不是单点，而是多轮决策累计偏差
4. **评估更复杂**：同一任务每次执行路径可能不同

**Harness Engineering 为什么重要**：
- 它不是“把 Agent 关进固定流程里”，而是给 Agent 提供 **高质量地图、工具、约束和反馈回路**
- OpenAI 这类实践强调的重点不是“规定 1、2、3、4 步”，而是：
  - 让代码仓库对 Agent 可读
  - 用文档、执行计划、规则、Lint、测试、可观测性来约束输出
  - 让 Agent 可以自己运行、验证、修复、提 PR
- 本质上，Harness 是 **让自主编排可落地、可扩展、可治理** 的基础设施

**两种模式的对比**：

| 维度 | 强编排流程 | Agent 自主编排 | 混合模式（推荐） |
|------|------------|----------------|------------------|
| **可控性** | 最高 | 较低 | 高 |
| **灵活性** | 较低 | 最高 | 高 |
| **工程成本** | 前期高，后期维护也高 | 前期较快，但治理成本高 | 中等 |
| **泛化能力** | 较弱 | 最强 | 较强 |
| **安全治理** | 容易做 | 难度大 | 可平衡 |
| **适合任务** | 固定流程任务 | 开放式复杂任务 | 大多数真实 Coding 任务 |

**Claude Code 和 Cursor 更接近哪种？**：

**更准确的说法是：两者都属于“带强约束的自主编排”，不是纯强编排。**

- **Claude Code**：
  - 更接近 **自主编排 + 强 Harness**
  - 公开能力强调检查点（Checkpoint）、Hook、Subagent、后台任务、终端执行
  - 说明它不是靠固定 DAG 驱动，而是允许 Agent 在目标约束下自主探索和修复
  - 但它又通过权限、回滚、工具边界、项目文档等方式增强可控性

- **Cursor**：
  - 更接近 **IDE 原生的自主编排 + 项目级规则约束**
  - 公开能力强调 Agent 模式、Rules、Memories、代码库索引、Subagent、MCP
  - 说明其核心也不是固定流程，而是基于上下文和工具进行动态决策
  - 但它在 IDE 内通过 Diff 审阅、规则、上下文选择和交互式确认，把自治程度做了可视化约束

**所以，如果一定要分类**：
- `Claude Code`：更偏 **自主编排**
- `Cursor`：也是 **自主编排**，但更偏 **IDE 引导式 / 交互式约束**
- 两者都不是“纯状态机式强编排系统”

**自研 Coding Agent 的 3 种常见方案**：

| 方案 | 做法 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| **方案 A：纯强编排** | 预定义 DAG / 状态机 / 固定节点 | 最稳、最好审计 | 泛化差、维护重 | 企业固定流程，如规范化代码迁移 |
| **方案 B：纯自主编排** | Agent 自己决定搜索、编辑、执行、验证顺序 | 灵活、泛化强 | 风险高、调试难 | 研究探索、小范围内部试验 |
| **方案 C：混合式 Harness** | 外层流程控制 + 内层 Agent 自主执行 | 平衡控制与效果 | 系统设计更复杂 | 生产级 Coding Agent，最推荐 |

**如果自己落地，推荐路线**：
1. **第一阶段**：先做强编排最小闭环
   - 例如：定位文件 -> 改代码 -> 跑 Lint -> 跑单测 -> 生成 Diff
   - 先把权限、安全、审计、验证打牢

2. **第二阶段**：把局部节点放开给 Agent 自主编排
   - 例如：允许 Agent 自主搜索相关文件、决定先修哪个测试、决定是否需要补测试

3. **第三阶段**：建设 Harness 基础设施
   - 项目规则、仓库文档、执行计划、结构化 lint、自定义工具、可观测性、回滚点

4. **第四阶段**：再扩展到长任务和后台执行
   - 如 Issue -> 修复 -> 验证 -> PR

**如何做方案选型**：
- 如果你的场景是 **高度标准化、风险很高、审批复杂**：
  - 优先强编排
- 如果你的场景是 **复杂代码库、开放式开发任务、希望高泛化**：
  - 优先混合式 Harness
- 如果你的场景还在 **原型探索期**：
  - 可以先用自主编排快速验证，但必须尽快补权限和验证系统

**一句话判断标准**：
> 当任务越开放、仓库越复杂，就越需要 Agent 自主编排；当风险越高、合规越强，就越需要强编排和治理层；真正能上线的系统，通常是两者结合。

**评分要点**：
- 3 分：能区分强编排和自主编排的基本差异
- 4 分：能结合 Claude Code、Cursor 说明它们更接近“受约束的自主编排”
- 5 分：能提出混合式 Harness 方案，并给出自研落地的阶段性路线

## 三、上下文工程与工具系统

### Q3.1 Coding Agent 如何做好代码库理解和上下文工程？ ⭐⭐⭐⭐

**问题**：
> 一个 Coding Agent 最容易失败的地方之一，是“没有看对上下文”。如果面对一个中大型代码库，你会如何设计它的代码库理解和上下文工程？

**期望答案**：

**上下文工程的目标不是“喂更多”，而是“喂更准”**。

**推荐的多层上下文体系**：

| 层次 | 内容 | 作用 |
|------|------|------|
| **即时上下文** | 当前文件、当前选区、报错信息、用户最近操作 | 贴近当前问题 |
| **局部上下文** | 相邻文件、调用链、导入关系、测试文件 | 理解附近逻辑 |
| **全局上下文** | 仓库索引、符号关系、语义搜索、配置文件 | 理解项目结构 |
| **历史上下文** | Git 变更历史、近期 PR、历史对话 | 理解“为什么这样设计” |
| **规则上下文** | 编码规范、架构约束、团队约定 | 控制输出风格和边界 |

**常见实现方式**：
1. **词法搜索**：适合精确找符号、配置、字符串
2. **语义搜索 / 向量索引**：适合模糊定位“相关实现”
3. **符号级分析**：函数、类、调用图、引用关系
4. **结构化元数据**：语言类型、测试目录、依赖图、构建系统
5. **运行反馈**：测试失败栈、编译错误、Lint 报错

**代码库索引的推荐内容**：
- 文件路径和语言类型
- 类 / 函数 / 接口 / 导出符号
- 调用关系和引用关系
- README、设计文档、配置文件
- 关键目录摘要（如 `src/`、`tests/`、`scripts/`、`infra/`）

**检索策略最佳实践**：
1. 用户问题先判断意图：修 Bug、加功能、重构、解释代码
2. 不同意图走不同检索路径
3. 先粗搜相关文件，再精读关键代码块
4. 尽量只把“与当前步骤最相关”的上下文送给模型

**常见误区**：
1. 把整个仓库一股脑塞给模型，导致上下文污染
2. 只做向量搜索，不做精确符号检索
3. 忽略报错栈和测试输出这类最强信号
4. 不考虑文件新鲜度，拿到旧版本代码或无关历史

**评分要点**：
- 3 分：知道要做文件搜索和上下文裁剪
- 4 分：能讲清即时、局部、全局、历史等多层上下文
- 5 分：能设计索引、检索、重排序、意图路由的完整上下文系统

---

### Q3.2 Coding Agent 需要哪些核心工具？编辑执行链路应该怎么设计？ ⭐⭐⭐⭐

**问题**：
> 一个真正能落地的 Coding Agent，至少需要哪些工具？它的编辑和执行链路应该如何设计，才能既高效又可控？

**期望答案**：

**核心工具集合**：

| 类别 | 典型工具 | 作用 |
|------|----------|------|
| **读取类** | 读文件、列目录、查看配置 | 获取精确上下文 |
| **搜索类** | 关键词搜索、语义搜索、符号搜索 | 快速定位代码 |
| **编辑类** | Patch / Diff 编辑、结构化编辑 | 修改代码 |
| **执行类** | Shell、测试、构建、Lint | 获取确定性反馈 |
| **版本控制类** | Git status / diff / log / commit | 理解和管理变更 |
| **外部连接类** | Web、MCP、Issue / PR 接口 | 获取外部上下文 |

**推荐的编辑链路**：

```
定位目标文件
   ↓
读取相关代码块
   ↓
生成最小必要修改
   ↓
以 Diff / Patch 形式写入
   ↓
运行 Lint / Test / Build 验证
   ↓
根据结果继续修正或结束
```

**为什么优先用 Diff / Patch，而不是整文件重写**：
1. 变更更小，更容易审查
2. 能降低误删用户代码的风险
3. 更适合多轮迭代和局部修复
4. 更利于与 Git、Code Review 工作流衔接

**命令执行的设计原则**：
1. 长命令支持后台执行和状态检查
2. 命令输出必须回灌给 Agent 作为观测结果
3. 明确区分只读命令、可写命令、高风险命令
4. 尽量避免破坏性操作，特别是危险 Git 命令

**为什么 Tool Use 是 Coding Agent 的核心护城河**：
- 代码生成本身会越来越同质化
- 真正决定完成率的是：
  - 工具是否全
  - 工具是否稳定
  - 权限和沙箱是否合理
  - 观测反馈是否能被 Agent 正确利用

**评分要点**：
- 3 分：知道读文件、搜索、编辑、跑测试是必备工具
- 4 分：能讲清 Diff 编辑和命令执行的基本链路
- 5 分：能从工具分层、权限控制、观测回灌解释完整执行系统

### Q3.3 RAG 对 Coding 到底有没有意义？ ⭐⭐⭐⭐

**问题**：
> 在 AI Coding / Coding Agent 场景里，是否真的需要构建 RAG？代码场景下的 RAG 和传统知识库问答中的 RAG 有什么不同？它的价值和边界分别是什么？

**期望答案**：

**先下结论**：
> 对中大型代码库来说，RAG 很有意义，但在 Coding 场景里，更准确的说法通常不是“传统知识库 RAG”，而是 **代码库检索（Code Retrieval）/ 上下文引擎（Context Engine）**。

**为什么对 Coding 有意义**：
1. **降低上下文成本**：不可能把整个仓库都塞给模型，需要先检索再精读
2. **提升定位能力**：帮助找到相关函数、调用链、测试、配置、文档、历史实现
3. **减少幻觉和误改**：让 Agent 基于真实仓库上下文做修改，而不是“脑补架构”
4. **适合大仓库 / 多模块场景**：仓库越大，检索系统越重要

**但它不是万能的**：
- Coding 场景不是“检索几段文本 -> 直接生成答案”这么简单
- 真正可靠的系统必须把 **检索 + 精确读文件 + 编辑 + 测试验证** 串起来
- 只做向量检索而不做精确搜索、符号分析和运行验证，效果通常不够好

**代码 RAG vs 传统文档 RAG**：

| 维度 | 传统文档 RAG | 代码场景 RAG / Retrieval |
|------|--------------|--------------------------|
| **检索对象** | 段落、文档块 | 函数、类、接口、配置、测试、调用关系 |
| **核心目标** | 回答问题 | 找对代码、改对位置、补全执行上下文 |
| **正确性要求** | 语义相关即可 | 既要相关，也要精确到符号和文件 |
| **新鲜度要求** | 小时 / 天级可接受 | 分钟级甚至秒级，尤其是当前分支 |
| **主要信号** | 语义相似度 | 关键词、符号、语义、调用图、Git diff、报错栈 |
| **输出形态** | 生成答案 | 定位上下文 + 驱动后续编辑和验证 |

**最佳实践：不要做“纯向量 RAG”，而要做混合检索**：
1. **关键词 / Grep 搜索**：找精确符号、报错字符串、配置项
2. **语义搜索**：找概念相近的实现、相似模式、历史范式
3. **符号级索引**：函数、类、接口、调用关系
4. **运行时上下文**：Lint、编译错误、测试栈、最近编辑文件
5. **规则和文档**：README、架构文档、AGENTS / Rules、团队约束

**什么时候价值最大**：
- 中大型仓库
- 多语言 / 多模块系统
- 需要跨文件理解和修改
- 需要在陌生代码库中快速定位相关实现

**什么时候价值有限**：
- 非常小的仓库
- 只改当前文件里的局部逻辑
- 用户已经精确指出了文件和函数位置

**一句话理解**：
> Coding 里的 RAG 主要不是“回答用户”，而是“帮 Agent 找到足够准确且足够新的上下文”，从而支撑后续的编辑和验证。

**评分要点**：
- 3 分：知道代码场景也需要检索系统，不能全靠大上下文
- 4 分：能区分代码 Retrieval 和传统文档 RAG 的差异
- 5 分：能指出最佳实践是关键词、语义、符号、运行反馈结合，而不是纯向量搜索

---

### Q3.4 代码库变更很频繁时，如何做代码 RAG / 索引的新鲜度保障？ ⭐⭐⭐⭐⭐

**问题**：
> 如果代码库变更非常频繁，分支多、未提交修改也多，你会如何设计 Coding 场景下的 RAG / 索引系统，保证 Agent 拿到的是足够新的上下文？有哪些业内最佳实践？

**期望答案**：

**核心原则**：
> 对 Coding 来说，重点不是“做一个静态知识库”，而是做一个 **增量更新、分支感知、可回退、可降级** 的代码检索系统。

**为什么高频变更是难点**：
1. 代码经常改，旧 Embedding 很快过时
2. 当前分支和默认分支可能差异很大
3. 未提交改动往往恰恰是 Agent 最该优先看到的内容
4. 一次接口变更可能影响多个文件和调用链

**最佳实践 1：索引单位要按代码语义切分，而不是按固定 Token 切块**：
- 优先按 **函数、类、方法、接口、路由、测试用例** 切分
- 保留必要的 import、注释、所属模块信息
- 固定长度切块容易把一个函数拆断，降低检索和编辑准确率

**最佳实践 2：做增量索引，不做全量重建**：
- 用 `content_hash` / 文件哈希 / Merkle Tree 检测变化
- 只有变更的文件或符号重新解析、重新向量化
- 未变化的 Chunk 直接复用旧索引和 Embedding 缓存
- 删除文件时同步移除对应索引项

**最佳实践 3：分层处理“新鲜度”**：

| 层级 | 数据来源 | 新鲜度 | 用途 |
|------|----------|--------|------|
| **Hot Layer** | 当前工作区、未提交改动、最近编辑文件、报错栈 | 最高 | 当前任务优先上下文 |
| **Warm Layer** | 当前分支的本地 / 远端索引 | 高 | 主要代码检索 |
| **Cold Layer** | 默认分支、历史 PR、设计文档、已归档知识 | 较低 | 补充背景信息 |

**最佳实践 4：查询时必须做“最终新鲜读取”**：
1. 检索阶段可以先用索引快速召回
2. 但在真正解释代码或修改代码前，应重新从当前工作树直接读取 Top-K 候选文件
3. 如果发现文件的 `mtime`、哈希或 Git 状态已经晚于索引时间，就应优先以本地文件内容为准

**最佳实践 5：分支感知（Branch-aware）非常重要**：
- 当前分支应优先于默认分支
- 不同分支最好有隔离索引 / 命名空间，避免上下文串线
- 切分支后，应触发轻量级增量校验或后台重建
- 对未提交变更，可在“远端索引 + 本地 working tree”之上做一层 overlay

**最佳实践 6：排序不能只看语义相似度**：

| 排序信号 | 作用 |
|----------|------|
| **关键词精确匹配** | 找类名、函数名、报错串、配置项 |
| **语义相似度** | 找相似实现和相关概念 |
| **符号 / 调用关系** | 找定义、引用、调用链 |
| **文件新鲜度** | 优先最近修改文件 |
| **分支 / 工作区优先级** | 优先当前任务上下文 |
| **运行时反馈** | 测试失败文件、编译错误相关文件优先 |

**最佳实践 7：索引里要带足够的元数据**：
- `path`
- `language`
- `symbol_name`
- `symbol_type`
- `module`
- `branch`
- `commit_sha`
- `content_hash`
- `indexed_at`
- `embedding_model_version`

**最佳实践 8：Embedding 缓存要和解析版本绑定**：
- 缓存键建议包含：
  - `content_hash`
  - `embedding_model_version`
  - `parser_version`
- 否则即便代码没变，解析器规则变了也可能导致旧索引不再可信

**最佳实践 9：做好排除和降噪**：
- 默认排除：
  - `node_modules/`
  - `dist/`
  - `build/`
  - `coverage/`
  - 生成代码
  - 大型二进制或低价值文件
- 否则会严重污染检索结果

**最佳实践 10：用正确的评估指标，而不是只看 RAG Recall**：
1. **Index Lag**：代码变更到可检索的延迟
2. **Stale Hit Rate**：检索到过期上下文的比例
3. **Wrong File Edit Rate**：改错文件的比例
4. **Top-K 命中率**：正确文件 / 符号是否进入候选集
5. **Task Completion Rate**：最终任务完成率

**业内通用方向总结**：
- Cursor / Sourcegraph 一类产品的公开实践都指向：
  - **增量索引**
  - **关键词 + 语义混合检索**
  - **代码语义单元切分**
  - **当前工作区优先**
- 本质上，大家都在把“代码 RAG”做成 **动态索引系统**，而不是静态向量库

**推荐落地方案**：
1. **最小可用版**：
   - `grep + 文件读取 + Git diff + 最近编辑文件优先`
2. **进阶版**：
   - 增加符号级索引、语义搜索、增量更新、Embedding 缓存
3. **生产版**：
   - 分支隔离、工作区 overlay、后台重建、回退策略、监控和评估体系

**一句话结论**：
> 高频变更代码库下，代码 RAG 仍然有意义，但必须从“静态知识库思维”升级为“动态上下文基础设施思维”。

**评分要点**：
- 3 分：知道代码索引要增量更新，不能频繁全量重建
- 4 分：能说出分支感知、最终新鲜读取、混合检索等关键机制
- 5 分：能设计包含增量索引、Working Tree Overlay、排序信号和评估指标的完整方案

## 四、工程化落地与评估

### Q4.1 如果在企业内落地一个 AI Coding 产品，技术方案会怎么设计？ ⭐⭐⭐⭐

**问题**：
> 如果你要在企业内部落地一个 AI Coding / Coding Agent 产品，既要支持 IDE 内协作，也要支持真实仓库执行和审计，你会如何设计整体技术方案？

**期望答案**：

**推荐采用“交互层 + 编排层 + 执行层 + 治理层”的分层架构**：

```
IDE / Terminal / Web
        ↓
Agent Orchestrator（任务编排）
        ↓
Context Service（索引、检索、规则）
        ↓
Execution Sandbox（文件编辑、Shell、测试、Git）
        ↓
Evaluation / Audit / Policy
```

**分层说明**：

| 层 | 职责 | 关键设计点 |
|----|------|------------|
| **交互层** | IDE 面板、终端、Diff 审阅、确认按钮 | 让用户随时接管和确认 |
| **编排层** | 任务拆解、工具调度、循环执行 | 控制 Agent 的核心流程 |
| **上下文层** | 代码库索引、搜索、规则、记忆 | 决定 Agent 的“理解质量” |
| **执行层** | 文件编辑、命令运行、测试、Git | 必须受控、可回放、可审计 |
| **治理层** | 权限、审计、评估、成本监控 | 满足企业合规和安全要求 |

**企业落地的常见阶段**：
1. **阶段 1：补全 + Chat**
2. **阶段 2：局部编辑 + 多文件修改**
3. **阶段 3：本地 Agent（能跑测试、修问题）**
4. **阶段 4：后台 / 云端 Agent（Issue -> PR、CI 协同）**

**架构选型建议**：
- **IDE-first**：更适合日常研发提效，审阅体验好
- **Terminal-first**：更适合后端、脚本化、复杂命令驱动场景
- **Hybrid**：最常见，IDE 做交互与 Diff，后台 Runner 做受控执行

**必须考虑的企业问题**：
1. 私有代码和密钥不能外泄
2. 不同仓库、不同团队有不同规则和权限
3. 需要记录 Agent 做过什么、为什么这么做
4. 需要可回滚、可追溯、可评估

**评分要点**：
- 3 分：知道企业落地不只是接一个模型 API
- 4 分：能设计交互、编排、执行、治理的分层架构
- 5 分：能结合 IDE、沙箱、审计、权限、云端 Agent 给出完整方案

### Q4.2 如何评估一个 Coding Agent 的效果？ ⭐⭐⭐⭐⭐

**问题**：
> 对一个 AI Coding / Coding Agent 产品，应该如何建立评估体系？除了模型主观感觉“好不好用”，还有哪些可以量化的指标？

**期望答案**：

**评估要分 4 层**：

| 层次 | 指标 | 说明 |
|------|------|------|
| **任务层** | Task Completion Rate、Test Pass Rate、Build Pass Rate | 任务是否真的完成 |
| **交互层** | 首次有效 Diff 时间、用户接管率、中断率 | Agent 是否高效好协作 |
| **质量层** | Bug 引入率、回滚率、代码风格一致性 | 改动质量是否稳定 |
| **业务层** | 开发时长节省、PR 周期缩短、接受率 | 是否真正提升产出 |

**离线评估**：
1. 构造内部任务集：修 Bug、补测试、重构、迁移依赖、解释复杂逻辑
2. 为每个任务设置验收标准：测试通过、输出格式、关键文件变更
3. 使用可重复的真实仓库或裁剪后的基准仓库跑回归

**在线评估**：
1. 用户是否接受 Agent 生成的修改
2. 修改是否被后续快速回滚
3. 用户是否频繁打断或重做
4. 完成一个任务的总耗时和成本

**对 Coding Agent 来说，最重要的不是“看起来聪明”，而是“是否完成了可验证任务”**。

**推荐指标体系**：
1. **任务完成率**：给定任务在限制步数内是否完成
2. **验证通过率**：Lint / Build / Unit Test / E2E 通过情况
3. **最小化返工率**：用户是否只做小修小补，还是完全推翻
4. **工具使用成功率**：搜索、编辑、命令执行是否稳定
5. **安全事故率**：是否触发危险操作、泄露敏感信息、误删代码
6. **成本效率**：Token 消耗、平均执行轮数、平均完成时长

**难点**：
- 单纯用编程榜单并不能代表真实工程价值
- 真实项目里多文件、旧代码、依赖链、测试环境才是难点
- 需要把“模型能力”与“工具系统能力”拆开评估

**评分要点**：
- 3 分：知道要看任务是否完成、测试是否通过
- 4 分：能区分离线评估和在线评估
- 5 分：能建立覆盖完成率、质量、效率、安全、成本的多层指标体系

## 五、安全边界与未来趋势

### Q5.1 AI Coding / Coding Agent 的安全风险和治理重点有哪些？ ⭐⭐⭐⭐⭐

**问题**：
> Coding Agent 可以直接读代码、改代码、跑命令，因此它的风险比普通聊天机器人更高。你认为它的主要安全风险有哪些？应该如何治理？

**期望答案**：

**主要风险**：

| 风险类型 | 例子 |
|----------|------|
| **代码库内 Prompt 注入** | README、注释、测试数据中故意写入误导性指令 |
| **敏感信息泄露** | `.env`、密钥、私有 API、内部源码被读出或上传 |
| **危险命令执行** | 删除文件、重写 Git 历史、访问生产环境 |
| **供应链风险** | 误装恶意依赖、执行不可信脚本 |
| **质量回归** | 自动修改引入隐藏 Bug 或破坏架构约束 |
| **权限越权** | 本来只允许读文件，却执行了写操作或联网操作 |

**治理原则**：
1. **最小权限原则**：默认只读，需要时再升级权限
2. **沙箱隔离**：文件系统、网络、命令执行都要可控
3. **高风险操作二次确认**：提交、删除、部署、外网访问必须审批
4. **日志审计**：所有工具调用、Diff、命令、输出都可追溯
5. **密钥治理**：敏感文件脱敏、Secret 扫描、临时凭证

**具体治理措施**：
- 对工具做分级：只读 / 可写 / 高风险
- 对 Git 操作做限制：默认禁止 `reset --hard`、`push --force`
- 对 Shell 做策略控制：允许白名单命令，或通过沙箱容器执行
- 对外部连接做域名或服务级权限控制
- 对输出做敏感信息过滤和审查

**为什么 Coding Agent 的安全治理比普通 LLM 更难**：
1. 它不只是“说”，而是“做”
2. 风险来自 **外部输入、仓库内容、工具执行、用户授权** 的组合
3. 一次错误操作可能直接改变代码库状态或开发环境状态

**评分要点**：
- 3 分：知道会有密钥泄露、危险命令等风险
- 4 分：能提出权限分级、审批、审计、沙箱等治理手段
- 5 分：能系统性描述 Prompt 注入、供应链、越权、执行安全的整体治理框架

### Q5.2 AI Coding / Coding Agent 的下一阶段趋势是什么？ ⭐⭐⭐⭐

**问题**：
> 你怎么看 AI Coding / Coding Agent 的下一阶段发展？结合 Cursor、Claude Code 这类产品的演进，你认为未来的产品和技术重点会是什么？

**期望答案**：

**趋势判断**：

| 趋势 | 说明 |
|------|------|
| **从单 Agent 到多 Agent / Subagent** | 不同子代理分别负责搜索、改代码、写测试、做 Code Review |
| **从前台交互到后台执行** | 用户提需求后，Agent 在后台跑长任务，再回传 Diff / PR |
| **从 IDE 工具到研发工作流基础设施** | 不只服务编码，还覆盖 Issue、PR、CI、文档、发布 |
| **从临时上下文到长期记忆** | 规则、项目偏好、架构约束、团队经验可持续沉淀 |
| **从封闭工具到标准化工具生态** | MCP 一类协议让工具接入和权限治理更标准 |
| **从模型竞争到系统竞争** | 真正决定体验的是上下文、工具、评估、安全、产品工作流 |

**未来最重要的能力**：
1. **更强的代码库理解**：不仅能搜到代码，还能理解架构意图
2. **更强的长任务自治**：Issue -> 设计 -> 改代码 -> 测试 -> PR
3. **更强的组织级记忆**：团队规则、最佳实践、历史决策沉淀
4. **更强的可评估性**：Agent 改得越多，越需要稳定评估和回归体系

**对产品形态的判断**：
- IDE 和终端不会二选一，而是会逐渐融合
- 本地 Agent 和云端 / 后台 Agent 会并存
- “写代码”只是入口，真正价值会延伸到整个软件交付链路

**一句话总结**：
> AI Coding 的竞争会从“谁补全更快”，演进到“谁能在真实研发流程中更安全、更稳定地完成复杂任务”。

**评分要点**：
- 3 分：知道未来会往更强 Agent 化方向发展
- 4 分：能说出多 Agent、后台执行、长期记忆、工具协议等趋势
- 5 分：能提出“模型能力会逐渐平权，系统与工作流能力才是核心壁垒”的判断
