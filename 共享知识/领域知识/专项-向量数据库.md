## 一、向量数据库基础

### Q1.1 向量数据库是什么 ⭐⭐

**问题**：
> 什么是向量数据库？它与传统关系型数据库有什么本质区别？在 AI 应用中扮演什么角色？

**期望答案**：

**定义**：
向量数据库是专门用于存储、索引和检索高维向量（Embedding）的数据库。它的核心操作是 ANN（Approximate Nearest Neighbor，近似最近邻）检索，而非传统的精确匹配查询。

**与关系型数据库对比**：

| 维度 | 关系型数据库（MySQL 等） | 向量数据库（Milvus 等） |
|------|------------------------|----------------------|
| **数据模型** | 行/列，结构化数据 | 高维浮点向量 |
| **查询方式** | SQL 精确匹配 | 相似度搜索（余弦/欧氏距离） |
| **索引类型** | B-Tree、Hash | HNSW、IVF、Annoy |
| **典型延迟** | 亚毫秒（简单查询） | 毫秒级（百万向量） |
| **核心场景** | 事务处理、精确查询 | 语义检索、推荐、去重 |

**在 AI 应用中的角色**：
1. **RAG 系统**：存储文档 Embedding（嵌入向量），支持语义检索
2. **推荐系统**：存储用户/物品 Embedding，做实时召回
3. **图像/音频搜索**：多模态 Embedding 的相似度匹配
4. **去重/聚类**：基于向量距离做数据去重和聚类分析

**评分要点**：
- 3 分：知道向量数据库用于存储和检索 Embedding
- 4 分：能对比与传统数据库的核心差异
- 5 分：能结合 RAG 等场景说明具体应用方式

### Q1.2 相似度度量方法 ⭐⭐

**问题**：
> 向量检索中常用的相似度度量方法有哪些？它们分别适合什么场景？

**期望答案**：

| 度量方法 | 公式含义 | 值域 | 适用场景 |
|---------|---------|------|---------|
| **Cosine Similarity（余弦相似度）** | 衡量向量方向的一致性，忽略长度 | [-1, 1] | 文本语义相似度（最常用） |
| **Euclidean Distance（欧氏距离）** | 衡量向量在空间中的绝对距离 | [0, +∞) | 图像特征、需要考虑绝对差异时 |
| **Inner Product（内积）** | 方向 + 长度的综合度量 | (-∞, +∞) | 向量已归一化时等价于余弦相似度，推荐系统打分 |
| **Hamming Distance（汉明距离）** | 二进制向量中不同位的个数 | [0, dim] | 二值化向量，极速粗筛 |

**选择建议**：
- 文本 Embedding（如 BGE、OpenAI Embedding）：优先用 **Cosine Similarity**
- 已归一化的向量：**Inner Product** 与 Cosine 等价，计算更快
- 需要考虑向量"强度"的场景：**Euclidean Distance**

**评分要点**：
- 3 分：知道 Cosine Similarity 是最常用的
- 4 分：能区分 Cosine 和 Euclidean 的适用场景
- 5 分：能解释归一化后 Inner Product 与 Cosine 等价的原因

## 二、索引算法原理

### Q2.1 ANN 索引算法对比 ⭐⭐⭐

**问题**：
> 向量数据库中常用的 ANN（Approximate Nearest Neighbor）索引算法有哪些？请对比它们的优缺点。

**期望答案**：

| 索引算法 | 原理 | 优点 | 缺点 | 适用场景 |
|---------|------|------|------|---------|
| **Flat（暴力搜索）** | 逐一计算距离 | 100% 召回率 | 极慢，O(n) | 小数据集基线测试 |
| **IVF（倒排文件索引）** | K-Means 聚类 → 只搜索最近的簇 | 速度快，支持 GPU | 需要训练，边界问题 | 百万级数据 |
| **HNSW（层次可导航小世界图）** | 多层跳表式图结构 | 高召回 + 低延迟 | 内存占用大 | 对延迟敏感的场景（主流选择） |
| **Annoy** | 随机投影树 | 内存友好，支持 mmap | 不支持动态更新 | 静态数据集 |
| **ScaNN** | 各向异性量化 | Google 出品，高性能 | 生态较小 | 大规模检索 |
| **DiskANN** | 基于磁盘的图索引 | 支持超大规模（十亿级） | 查询延迟略高 | 数据超出内存时 |

**HNSW 详解**：
- 构建多层图结构，上层稀疏（长距离跳转）、下层稠密（精确搜索）
- 搜索从最上层开始，逐层下降，在每层做贪心搜索
- 关键参数：`M`（每个节点的连接数）、`efConstruction`（构建时搜索宽度）、`efSearch`（查询时搜索宽度）
- M 越大 → 召回越高，内存越大；efSearch 越大 → 召回越高，延迟越大

**IVF 详解**：
- 先用 K-Means 将向量聚成 `nlist` 个簇
- 查询时只搜索最近的 `nprobe` 个簇
- nprobe 越大 → 召回越高，速度越慢
- 可与 PQ（Product Quantization，乘积量化）结合：IVF_PQ，用量化降低内存

**评分要点**：
- 3 分：知道 HNSW 和 IVF 两种主要算法
- 4 分：能解释 HNSW 的多层图结构原理
- 5 分：能对比多种算法并根据场景选择

### Q2.2 向量量化技术 ⭐⭐⭐⭐

**问题**：
> 什么是向量量化（Vector Quantization）？PQ（Product Quantization）和 SQ（Scalar Quantization）有什么区别？

**期望答案**：

**为什么需要量化**：
- 原始向量（float32 × 1536维）：每条 6KB
- 1 亿条向量：~600GB 内存 → 成本极高
- 量化可将内存降低 4-32 倍，同时保持高召回率

**量化方法对比**：

| 方法 | 原理 | 压缩比 | 召回率损失 | 适用场景 |
|------|------|--------|----------|---------|
| **SQ（标量量化）** | 将 float32 逐元素映射为 int8/uint8 | 4× | 极小（<1%） | 通用场景，首选尝试 |
| **PQ（乘积量化）** | 将高维向量切分为子空间，每个子空间独立聚类编码 | 16-32× | 中等（2-5%） | 内存极度受限 |
| **BQ（二值量化）** | 每维映射为 0/1 | 32× | 较大 | 粗筛阶段 |

**PQ 原理**：
1. 将 D 维向量切分为 M 个子向量（如 1536 维切 96 组，每组 16 维）
2. 对每组子向量做 K-Means 聚类（通常 K=256，用 8 bit 编码）
3. 每个子向量只存聚类 ID（1 byte），原来 64 byte 变 96 byte → 压缩至 ~6%
4. 查询时用预计算的距离表快速累加

**SQ 原理**：
- 统计每一维的 min/max 值
- 将 float32 线性映射到 [0, 255]（int8）
- 简单高效，召回率损失极小

**评分要点**：
- 3 分：知道量化是为了减少内存
- 4 分：能解释 PQ 的子空间分割和编码思路
- 5 分：能对比 SQ/PQ/BQ 并给出选型建议

### Q3.1 主流向量数据库对比 ⭐⭐⭐

> 目前主流的向量数据库有 Milvus、Qdrant、Chroma、Weaviate、Pinecone（松果），它们各有什么特点？如何选型？

**期望答案**：

**产品对比**（基于 2026 Q1 基准测试）：

| 维度 | Milvus | Qdrant | Chroma | Weaviate | Pinecone |
|------|--------|--------|--------|----------|----------|

| **查询延迟（1M 向量 p50）** | ~6ms | ~4ms | ~12ms | ~12ms | ~8ms |
| **索引类型** | 8 种（最全） | HNSW 为主 | HNSW | HNSW | 私有实现 |
| **GPU 加速** | ✅ 支持 | ❌ | ❌ | ❌ | ❌ |

| 混合搜索（向量 + 关键词） | **Weaviate** | 内置 BM25，GraphQL API |
| 零运维 / 全托管 | **Pinecone** | 无需管理基础设施 |

**成本参考（10M 向量）**：
- Chroma（自托管）：$0（开源）
- Qdrant Cloud：~$45/月
- Weaviate Cloud：~$65/月
- Pinecone：~$70/月

## 四、生产实践与调优

### Q4.1 RAG 场景下的向量检索调优 ⭐⭐⭐⭐

**问题**：
> 在 RAG 系统中，向量检索的召回率不理想，你会从哪些方面进行调优？

**期望答案**：

**调优层次**：

| 层次 | 调优方向 | 具体方法 |
|------|---------|---------|
| **Embedding 模型** | 选择更好的 Embedding 模型 | BGE-M3（多语言多粒度）、GTE-Qwen2 等；在领域数据上微调 Embedding |
| **分块策略** | 优化文档切分方式 | 语义分块 > 固定长度；设置 overlap（重叠）；根据文档类型选择策略 |
| **索引配置** | 调整索引参数 | HNSW: 增大 M 和 efSearch；IVF: 增大 nprobe |
| **查询优化** | 改进检索方式 | Query 改写 / HyDE；混合检索（向量 + BM25 + RRF 融合） |
| **后处理** | 精排和过滤 | Reranker 重排序（如 BGE-Reranker）；元数据过滤 |

**常见问题排查清单**：
1. **Embedding 模型不匹配**：Query 和 Document 使用了不同的 Embedding 模型
2. **分块粒度不当**：Chunk 太大导致语义稀释，太小导致上下文丢失
3. **Top-K 过小**：召回候选不足，应配合 Reranker 使用更大的 Top-K
4. **距离度量选择错误**：Embedding 已归一化却用了 Euclidean Distance

**评分要点**：
- 3 分：能说出 1-2 个调优方向
- 4 分：能系统性地从 Embedding、索引、查询多层次分析
- 5 分：能给出具体参数建议和排查思路

### Q4.2 Milvus 中的增量更新与一致性设计 ⭐⭐⭐⭐⭐

**问题**：
> 在 RAG 系统里，如果一个源文档被切成多个 Chunk，且内容会频繁更新，你如何基于 Milvus 设计增量更新方案？怎样避免重复计算 Embedding、避免查询空窗期，并保证新旧版本切换的一致性？如果是单条商品信息更新，又该如何做实时处理？

**期望答案**：

**先澄清一个关键点**：
- Milvus 支持 `upsert`，适合基于稳定主键更新单条向量/记录
- 但对“一个源文档 -> 多个 Chunk”的场景，真正难点不是单条记录能不能改，而是：
  1. 重新分块后 Chunk 数量可能变化
  2. 新旧 Chunk 可能短时间混杂
  3. 先删后写会出现查询空窗期
  4. 需要保证检索侧读到的是同一版本

**推荐的数据模型**：

| 字段 | 用途 |
|------|------|
| `source_id` | 源文档或源商品的稳定 ID |
| `chunk_id` | Chunk 唯一 ID（可由 `source_id + chunk_index + version` 生成） |
| `doc_version` | 文档版本号 / 时间戳 |
| `content_hash` | Chunk 内容哈希，用于判断是否需要重算 Embedding |
| `embedding_model_version` | Embedding 模型版本，避免混用不同向量空间 |
| `is_active` | 当前是否对查询可见 |
| `updated_at` | 更新时间，便于排障和回溯 |

**推荐更新链路（文档级）**：

1. **变更感知**：通过 CDC / MQ / 定时扫描捕获源文档变更
2. **结构化清洗**：统一标题、正文、标签、权限等字段
3. **重新分块**：按最新 Chunking 策略切分
4. **缓存复用**：对每个 Chunk 计算 `content_hash`，未变化的 Chunk 直接复用 Embedding 缓存
5. **先增后删**：先写入新版本 Chunk，再切换查询可见版本，最后异步删除旧版本
6. **校验发布**：校验 Chunk 数、抽样检索、监控延迟后再清理旧数据

**Embedding 缓存最佳实践**：
- 使用 `CacheBackedEmbeddings` 或自定义 KV Cache，避免重复对相同文本做向量化
- `namespace` 应绑定 Embedding 模型名 / 版本，避免不同模型缓存污染
- 文档 Embedding 缓存收益通常最大；Query Embedding 是否缓存取决于查询重复度

**两种常见切换方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **同 Collection 版本过滤** | 新旧版本共存，查询时按 `doc_version` / `is_active` 过滤 | 实现简单，便于渐进迁移 | 过滤逻辑更复杂 |
| **影子 Collection + Alias 切换** | 新版本写入 shadow collection，验证后切 alias | 切换原子性更好，适合大批量重建 | 需要更多存储和运维 |

**为什么推荐“先增后删”而不是“先删后增”**：
- 先删后增会导致短时间内检索不到任何 Chunk，出现查询空窗期
- 先增后删可以保证读路径始终有可用版本
- 当新版本校验失败时，旧版本仍可回滚继续服务

**单条商品信息的实时更新方案**：
1. 商品主数据变更后发 MQ 事件
2. 消费端将结构化字段映射为标准文本模板，如“标题 + 卖点 + 类目 + 品牌 + 属性”
3. 若该商品只对应 1～数个稳定 Chunk，可直接基于稳定主键执行 Milvus `upsert`
4. 若商品描述改动会影响分块数量或 Chunk 边界，仍应走版本化写入而非简单覆盖
5. 同时更新元数据字段，便于类目、上架状态、渠道过滤

**适用边界**：
- **`upsert` 更适合**：单条记录、Chunk 边界稳定、主键固定的场景
- **版本化双写更适合**：长文档、多 Chunk、批量重建、需要零空窗切换的场景

**监控指标**：
1. 数据新鲜度（源数据更新时间到可检索时间的延迟）
2. Embedding 缓存命中率
3. Upsert / 写入失败率
4. 版本切换成功率
5. 检索命中率与空结果率

**评分要点**：
- 3 分：知道可以用版本号、MQ、Upsert 做增量更新
- 4 分：能区分单条记录更新和多 Chunk 文档更新的不同策略
- 5 分：能讲清 Embedding 缓存、先增后删、版本过滤 / Alias 切换等生产级方案

### Q4.3 向量数据库高可用架构 ⭐⭐⭐⭐⭐

**问题**：
> 如何设计一个高可用的向量数据库集群？以 Milvus 为例，描述其分布式架构。

**期望答案**：

**Milvus 分布式架构**：

```
                    ┌──────────────┐
                    │   Proxy      │  ← 接入层：负载均衡、鉴权、路由
                    └──────┬───────┘
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
  │  Query Node  │ │  Data Node   │ │  Index Node  │
  │  （查询节点） │ │  （数据节点） │ │  （索引节点） │
  └──────┬───────┘ └──────┬───────┘ └──────┬───────┘
         │                │                │
         ▼                ▼                ▼
  ┌─────────────────────────────────────────────┐
  │            Object Storage（S3/MinIO）        │  ← 存储层：数据持久化
  │            + etcd（元数据）                   │
  │            + Pulsar/Kafka（日志流）            │
  └─────────────────────────────────────────────┘
```

**核心组件职责**：

| 组件 | 职责 | 可扩展性 |
|------|------|---------|
| **Proxy** | 请求路由、负载均衡 | 无状态，水平扩展 |
| **Query Node** | 执行向量检索 | 按 Segment 分片，水平扩展 |
| **Data Node** | 数据写入和持久化 | 按 Channel 分片 |
| **Index Node** | 构建向量索引 | 按任务分配，弹性伸缩 |
| **etcd** | 元数据管理、服务发现 | 3-5 节点高可用 |
| **MinIO/S3** | 数据和索引的持久化存储 | 对象存储天然高可用 |
| **Pulsar/Kafka** | WAL 日志，保证数据不丢失 | 分布式消息队列 |

**高可用设计要点**：
1. **存算分离**：计算节点无状态，故障后可快速重建
2. **多副本**：Segment 支持多副本，查询节点可做读扩展
3. **WAL 日志**：写入先落 Pulsar/Kafka，保证数据持久性
4. **故障转移**：节点故障后由 Coordinator 重新分配 Segment

**评分要点**：
- 3 分：知道向量数据库需要分布式部署
- 4 分：能描述存算分离架构的基本思路
- 5 分：能详细描述 Milvus 各组件职责和高可用机制
